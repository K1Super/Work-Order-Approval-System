# 编码规范

本文档整合项目级开发约束与企业级工程规范。

## 1. 项目开发规范与治理

### 1.1 代码规范

- **命名规范**：Java 类名大驼峰，方法/变量小驼峰，常量全大写下划线分隔。
- **注释规范**：类、方法必须包含 JavaDoc，复杂业务逻辑必须注释。
- **分层规范**：Controller 不写业务逻辑，ServiceImpl 不写 SQL，Mapper 不写业务逻辑。
- **异常规范**：业务异常使用 `BusinessException`，禁止直接抛 `RuntimeException`。

### 1.2 安全红线

1. **禁止使用 ScriptTask**：BPMN 解析阶段拦截。
2. **禁止使用 `${}` 拼接 SQL**：全部使用 `#{}`。
3. **禁止使用 `v-html`**：全部替换为 `v-safe-html`。
4. **禁止生产环境弱密钥**：JWT/AES/HMAC 密钥启动硬断。
5. **禁止 DevTools 进入生产**：`excludeName` 显式排除。
6. **禁止匿名访问业务接口**：除登录、密码重置外全部需认证。

### 1.3 审计规范

- 所有业务表必须包含审计字段。
- 删除操作必须逻辑删除，记录 `update_by` 和 `update_time`。
- 审批操作、登录登出、密码变更、权限变更必须记录审计日志。

### 1.4 Git 分支规范

| 分支 | 用途 |
|------|------|
| `main` | 生产发布分支 |
| `develop` | 开发集成分支 |
| `feature/*` | 功能开发分支 |
| `bugfix/*` | 缺陷修复分支 |
| `hotfix/*` | 生产热修复分支 |

## 2. 企业级研发统一规范

### 2.1 企业级 API 设计规范

#### 文档目的
统一全公司 RESTful API 设计风格，降低前后端、服务间调用对接成本，保证接口易用、一致、可维护。

#### 适用范围
所有对外、对内 HTTP/HTTPS API，包括 Web、H5、小程序、OpenAPI、微服务间调用。

#### URL 设计
- 使用名词复数形式
- 层级关系通过路径体现
- 禁止出现动词：避免 `/getUser`，用 `GET /users/{id}`
- 版本控制：URL 前缀
- 路径全小写，单词间用连字符

#### HTTP 方法
- `GET`：获取资源
- `POST`：创建资源
- `PUT`：全量更新资源
- `PATCH`：部分更新资源
- `DELETE`：删除资源

#### 请求与响应格式
- 统一使用 JSON，请求头 `Content-Type: application/json`
- 请求体所有字段采用 camelCase（或 snake_case，根据团队共识全栈统一）
- 响应体固定结构：
```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "xxx"
}
```
- `code` 为业务状态码，0 表示成功，非 0 为错误码
- 分页响应统一格式：
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [],
    "page": 1,
    "page_size": 20,
    "total": 100
  }
}
```

#### HTTP 状态码
- `200`：成功
- `201`：创建成功
- `400`：参数错误
- `401`：未认证
- `403`：无权限
- `404`：资源不存在
- `409`：资源冲突
- `422`：业务校验失败
- `500`：服务端内部错误

#### 错误返回
- 必须返回 `code`、`message`、`trace_id`
- `message` 应为中文描述，面向调用方友好
- 详细错误字段可增加 `errors` 数组，精确到字段级别

#### 鉴权
- 所有需要登录的接口，统一在请求头携带 `Authorization: Bearer {token}`
- API 签名校验（如 OpenAPI）统一使用 `X-Signature`、`X-Timestamp`、`X-Nonce` 等头

#### 过滤、排序与搜索
- 过滤：`GET /users?status=active&role=admin`
- 排序：`?sort=-created_at,id`（`-`表示降序）
- 搜索：`?q=关键词`，或 `?name_like=张三`

#### 版本废弃
- 不能直接删除旧版本，必须先标记为 `Deprecated`
- 在响应头中增加 `Sunset` 或 `Deprecation` 通知调用方
- 至少保留一个版本过渡期

#### 自动化检验
- 通过 OpenAPI/Swagger 文档自动生成和校验
- CI 集成交互校验：URL 风格、请求方法、响应体结构、状态码使用是否合规

### 2.2 错误码规范

#### 文档目的
建立全局统一错误码体系，实现错误精准识别、快速定位、国际化与自动化处理。

#### 适用范围
前后端所有服务、中间件、网关等产生的业务与系统错误。

#### 错误码结构
三段式：`{系统}-{模块}-{具体错误}`
- 系统码：2 位数字，公司统一分配
- 模块码：3 位数字，系统内自定
- 错误编号：3 位数字

示例：`01-002-003` 用户系统(01) - 订单模块(002) - 库存不足(003)

#### 错误码注册
- 所有错误码必须在代码仓库中以**常量文件**或**错误码 SDK** 形式集中定义
- 每个错误码必须绑定：
  - 中文错误消息模板（支持占位符）
  - 英文翻译（国际化场景）
  - 建议 HTTP 状态码
  - 错误级别（错误/警告/信息）
- 新增错误码需走 Code Review，CI 自动化扫描未注册的魔法数字直接拦截

#### 使用方式
- 服务端抛出错误码常量，统一日志工具及全局异常处理器自动填充消息
- 响应体中 `code` 直接使用错误码字符串（如 "01-002-003"）
- 客户端可依据错误码执行特定逻辑，严禁基于 `message` 字符串判断

#### 常见系统码示例
- `01`：用户中心
- `02`：订单系统
- `03`：支付中心
- `04`：商品系统
- `99`：公共系统（如数据库异常、网络超时等）

#### 公共错误码
99-000-001：系统内部错误，HTTP 状态码 500
99-000-002：参数缺失或非法，HTTP 状态码 400
99-000-003：身份认证失败，HTTP 状态码 401
99-000-004：无访问权限，HTTP 状态码 403
99-000-005：请求太频繁，HTTP 状态码 429

#### 错误码模板绑定
统一错误消息应支持参数注入，例如：
`01-002-003` 模板："订单创建失败，商品{skuId}库存不足"
日志和返回消息可动态填充参数。

### 2.3 数据库设计规范

#### 文档目的
统一数据建模、命名、索引、SQL 编写标准，保障数据库性能与可维护性。

#### 适用范围
所有关系型数据库（MySQL/PostgreSQL 等），业务数据库与数仓 ODS 层。

#### 命名规范
- **库名**：小写+下划线，项目名缩写，如 `order_system`
- **表名**：小写+下划线，复数或单数一致（建议单数），如 `user`、`order_item`
- **字段名**：小写+下划线，如 `user_name`、`created_at`
- **索引名**：`idx_表名_字段名`，唯一索引 `uk_字段名`
- **主键**：统一 `id`，类型 bigint/unsigned int，自增或雪花算法
- 禁止使用保留字，避免拼音或英文混用

#### 必备基础字段
每个业务表强制包含：
- `id` 主键
- `create_time` datetime 或 timestamp，默认当前时间
- `update_time` datetime 或 timestamp，自动更新
- `is_deleted` tinyint 逻辑删除标记（可选，视业务决定物理还是逻辑删）

#### 字段类型
- 金额：必须用 `decimal(m,n)`，禁止 float/double
- 状态字段：`tinyint` 或 `varchar`，注释中明确每个值含义
- 长文本：`text`，禁止滥用 `varchar(65535)`
- 布尔：`tinyint(1)`
- 日期时间：`datetime` 或 `timestamp`，全表统一
- 避免使用 `NULL`，尽量设定默认值，字符串默认 `''`，数字默认 `0`

#### 索引规范
- 高频查询必须建索引，多字段查询创建联合索引
- 联合索引遵循最左前缀原则，区分度高的字段放前面
- 禁止在索引列上使用函数或表达式
- 单表索引数量建议不超过 5 个
- 大表 DDL 变更需在低峰期执行，并评估锁表风险

#### SQL 编写
- **禁止** `SELECT *`，必须明确字段
- 大批量操作（更新/删除）必须分批，配合 LIMIT
- 避免子查询，尽量 JOIN
- 使用 EXPLAIN 分析执行计划，SQL 上线前必须走型检查
- 动态 SQL 必须防注入（参数化查询）

#### 分库分表
- 分片键选取原则：高频查询条件，数据分布均匀
- 中间件：推荐 ShardingSphere 或自研 Proxy
- 全局唯一 ID 生成方案：雪花算法或统一发号器

#### 变更管理
- 所有 DDL/DML 脚本纳入版本控制，目录按版本组织
- 生产变更必须经过审核，提交执行计划及回滚方案
- 定期备份与恢复演练

### 2.4 代码风格与命名规范

#### 文档目的
统一团队编程风格，提升代码可读性、可维护性，减少 Code Review 争议。

#### 适用范围
所有业务代码，按语言分别定义（以 Java 为例，其他语言参考同样结构）。

#### 基本格式
- 缩进：4 个空格，禁止 Tab
- 单行最大 120 字符
- 大括号：K&R 风格（不换行）
- 文件编码：UTF-8
- 文件末尾保留一个空行

#### 命名规则
- **包名**：全小写，层级划分，如 `com.company.project.module`
- **类名**：大驼峰，名词或名词短语，如 `UserService`
- **方法名**：小驼峰，动词开头，如 `getUserById`
- **变量名**：小驼峰，有意义，避免 a/b/temp
- **常量**：全大写+下划线，如 `MAX_RETRY_COUNT`
- 布尔变量以 `is`/`has`/`can` 开头

#### 注释
- 类注释：使用 JavaDoc 风格，描述功能、作者、版本
- 公开方法注释：说明参数、返回、异常
- 复杂逻辑使用行注释解释“为什么”，而不是“做什么”

#### 代码组织
- 单一职责：每个类/方法只做一件事
- 方法长度建议不超过 50 行
- 避免过多参数，超 3 个封装为对象
- 禁止魔法值，使用常量或枚举

#### Lint 与格式化
- 统一使用 Checkstyle / ESLint / Prettier / Black 等工具
- 提交前通过 Git Hook 自动格式化及检查
- 所有 Lint 规则配置纳入仓库根目录，CI 中强制执行

### 2.5 分支管理与发布流程规范

#### 文档目的
规范代码分支策略、发布审批与回滚机制，保障交付流水线稳定可靠。

#### 适用模型
默认采用 **Trunk Based Development**（或 Git Flow，根据团队规模和交付节奏选定一种）。

#### 分支命名
- 主分支：`main` / `master`（受保护，禁止直接推送）
- 开发分支：`develop`（可选，视模型而定）
- 功能分支：`feature/{JIRA-ID}-short-desc`，如 `feature/PROJ-123-add-login`
- 修复分支：`bugfix/{JIRA-ID}-short-desc`
- 紧急修复：`hotfix/{version}-short-desc`
- 发布分支：`release/{version}`

#### 提交规范
推荐 [Conventional Commits](https://www.conventionalcommits.org/)：
```
<type>(<scope>): <subject>

[optional body]
```
类型：feat、fix、docs、style、refactor、perf、test、chore

#### 合并策略
- 向 `main` / `develop` 合并必须通过 Pull Request / Merge Request
- 至少 1 位同事 Code Review 通过后方可合并
- 合并时使用 `Squash and Merge` 或 `Rebase and Merge`（保持主干历史整洁）
- 所有合并必须通过 CI 自动化测试与 Lint 检查

#### 发布流程
- 发布版本号遵循语义化版本 `MAJOR.MINOR.PATCH`
- 从 `main` 拉取 `release/` 分支，预发环境验证通过后，打 Tag
- 生产发布需走审批单，记录发布内容、回滚方案
- 发布后监控关键指标及错误日志

#### 回滚
- 代码回滚：使用 `git revert` 或部署上一稳定版 Tag
- 数据库回滚：执行预准备的逆向 SQL 或通过数据补偿
- 回滚完成后需在 30 分钟内复盘

### 2.6 配置管理规范

#### 文档目的
统一配置中心接入、命名、加密和变更流程，消除硬编码与配置混乱。

#### 范围
应用配置、中间件参数、开关、业务字典等所有运行时配置。

#### 接入标准
- 所有环境（dev/test/pre/prod）统一通过 **配置中心**（Nacos/Apollo/Consul 等）管理
- 禁止将配置写在本地 properties 文件并随包发布（开发环境本地调试除外）
- 代码中通过 SDK 动态获取配置，支持热更新

#### 命名规范
- 格式：`{应用名}.{功能模块}.{key}`
- 示例：`order-service.payment.timeout`、`web-app.feature.new-checkout.enabled`
- 全小写，用点分隔，单词用短横线

#### 配置类型
- 静态配置：数据库连接、线程池大小等，变更需重启
- 动态配置：开关、阈值、黑白名单，必须支持运行时刷新
- 敏感配置：密码、密钥、Token，必须加密存储，配置中心显示为密文，应用内解密使用

#### 变更流程
- 配置变更必须通过配置中心管理后台操作，不可直接修改线上文件
- 生产配置变更需要至少一人审批，记录操作人与时间
- 动态配置变更后需验证应用是否生效，灰度逐步放开
- 配置中心操作需记录审计日志

#### 版本与回滚
- 配置中心保留历史版本，支持一键回滚
- 禁止随意删除正在使用的配置项

### 2.7 异常处理与返回值规范

#### 文档目的
统一异常分类、捕获及全局响应包装，提升系统健壮性与调用方体验。

#### 异常分类
- **业务异常（BizException）**：业务逻辑错误，如库存不足、用户已存在，需传递对应错误码
- **系统异常（SystemException）**：数据库连接失败、RPC 超时等，通常为 500 级别
- **校验异常（ValidationException）**：参数校验失败，如字段缺失、格式非法

#### 异常处理原则
- 严禁空 catch 块，捕获后必须处理或记录日志并抛出上层
- Controller 层通过全局异常处理器捕获所有未被处理的异常，统一返回 `Result` 对象
- 异常中必须携带错误码及必要的业务上下文
- 不允许把异常当作正常业务控制流使用
- 第三方调用异常需转换为内部异常，隐藏实现细节

#### 返回值包装
所有接口响应强制使用统一包装类 `Result<T>`：
```java
public class Result<T> {
    private String code;        // 错误码或 "0"
    private String message;
    private T data;
    private String traceId;
    // 静态方法：success(data), fail(code, message)
}
```
前端/调用方统一解析 `code` 判断成功与否。

#### 全局异常处理器
- 捕获 `BizException`：提取错误码和消息，返回 `Result.fail`
- 捕获 `MethodArgumentNotValidException`：返回 400 及字段错误详情
- 捕获所有未被捕获异常：返回 500，记录 ERROR 日志，包含堆栈

#### 前端异常边界
- 接口统一通过拦截器处理非 0 code，弹窗提示或路由跳转登录页（401）
- 全局捕获未处理 JavaScript 异常上报日志服务
- 异步 Promise 必须有 `.catch` 或 try/catch

### 2.8 安全开发规范

#### 文档目的
从编码源头预防安全漏洞，满足企业安全合规及等保要求。

#### 认证与授权
- 统一使用 OAuth2.0 + JWT 进行认证授权
- 密码存储必须加盐哈希（bcrypt/scrypt），严禁明文、MD5
- 登录失败次数限制，图形验证码/设备绑定的二次验证
- 敏感操作（支付、修改手机号）需二次鉴权
- Token 过期时间合理设置（Access Token 15 分钟，Refresh Token 7 天），并支持主动吊销

#### 输入验证
- 所有外部输入（请求参数、Header、Cookie）必须做校验与过滤
- 长度、类型、格式、范围严格匹配，白名单优先
- 防 SQL 注入：使用参数化查询或 ORM，禁止拼接 SQL
- 防 XSS：输出转义，前端对用户内容使用安全渲染
- 防 CSRF：关键操作使用 CSRF Token 或 SameSite Cookie

#### 文件上传
- 限制文件类型（白名单）、大小，禁止执行脚本
- 上传到独立文件服务器或 OSS，不同源访问，避免解析
- 文件名随机化，禁止保留原始文件名

#### 数据保护
- 敏感数据（身份证、手机号、银行卡）传输加密（TLS 1.2+），存储加密或脱敏
- 日志禁止明文记录敏感信息（参见日志规范）
- 数据库备份加密，访问权限控制

#### 依赖与组件
- 禁止引入存在高危漏洞的版本，及时升级
- 安全补丁优先级：严重漏洞 24 小时内修复

#### 日志与审计
- 所有认证、授权、关键业务操作必须产生审计日志
- 日志中不包含密码、Token 等敏感凭证

## 3. 企业级通用软件工程规范

适用范围：全行业企业级软件项目，适配Java/Go/Python后端、Vue/React前端、各类数据库、中间件及容器化部署架构，无技术栈绑定，可直接落地各类业务系统（OA、工单、审批、电商、管理平台等）

落地方式：直接放入项目 docs/DEVELOPMENT\_SPEC\.md，作为团队统一研发标准、新人入职规范、项目交付验收依据

### 3.1 总则

#### 1\.1 核心设计原则（全局强制约束）

所有研发工作、代码编写、架构设计、流程搭建必须遵循以下顶层原则，作为项目唯一评判标准：

1. 单一职责原则：类、方法、接口、组件仅负责单一功能，入口类仅启动服务，不承载任何业务逻辑。

2. 高内聚低耦合原则：模块内部功能高度聚合，模块间通过标准化接口通信，禁止硬编码耦合、跨模块直接调用内部逻辑。

3. 开闭原则：对功能扩展开放，对原有代码修改关闭，复杂分支、多场景逻辑通过设计模式优化，杜绝多层冗余if\-else。

4. 依赖倒置原则：高层业务逻辑依赖抽象接口，不依赖具体实现类，便于迭代扩展、替换实现方案。

5. 最小权限原则：系统账号、文件权限、接口访问、数据操作、服务调用均遵循最小可用权限，杜绝超权限配置。

6. 可观测性原则：日志、异常捕获、业务埋点、服务监控、链路追踪全覆盖，所有故障、问题可追溯、可定位、可复盘。

7. 环境隔离原则：开发、测试、预发、生产环境严格隔离配置、数据、资源，禁止生产环境开启调试、测试、冗余功能开关。

8. 可复用可维护原则：通用逻辑、工具方法、业务组件统一封装，代码简洁规范，便于迭代维护、多人协作。

#### 1\.2 通用技术栈标准化准则与技术选型准入标准

本规范不强制固定技术栈，仅定义企业级通用技术选型标准，各项目可根据业务场景适配，统一团队技术范式。所有新增技术、开源组件、框架、中间件必须遵循统一准入评审流程。

##### 1\.2\.1 基础技术选型方向

- 核心框架：采用主流稳定开源框架，优先官方长期维护版本，杜绝小众、废弃框架

- 权限体系：统一基于RBAC角色权限模型，支持接口级、数据级双层权限控制

- 数据层：使用标准化ORM框架，杜绝原生硬编码SQL，保证数据操作统一规范

- 数据存储：关系型数据库为主、缓存中间件为辅，复杂场景适配时序、文档数据库

- 版本管理：数据库脚本版本化管控，支持自动迁移、版本回溯

- 服务监控：接入通用监控、链路追踪组件，实现服务状态、接口性能、异常全监控

- 工具依赖：选用社区活跃、安全稳定的通用工具类，禁止自定义冗余底层工具

##### 1\.2\.2 技术选型准入评审强制规范（新增）

项目所有新增技术框架、开源组件、中间件、工具依赖，必须经过架构组评审通过后方可引入，禁止研发人员私自新增、替换技术依赖。评审核心维度如下：

1. 社区活跃度：核查项目Star数量、近期Commit频率、版本迭代节奏，杜绝长期停滞、无人维护的组件。

2. 安全风险：查询公开漏洞库，确认无高危、未修复漏洞，无历史重大安全事故。

3. 团队技术储备：匹配现有团队技术能力，避免引入学习成本过高、无人维护的技术体系。

4. 长期维护成本：评估版本迭代稳定性、文档完善度、问题排查成本，适配企业长期迭代需求。

5. 技术兼容性：与项目现有技术栈、工程架构、部署体系兼容，无版本冲突、架构冲突。

强制红线：禁止引入无官方LTS长期支持版本、已停止迭代、社区废弃的开源组件及框架。

#### 1\.3 通用术语与约束

- 强制规范：所有项目必须严格遵守，违规视为代码不合格，禁止合并上线

- 推荐规范：最优实践方案，新项目严格执行，存量迭代逐步优化

- 业务适配项：根据项目业务场景灵活调整，保持整体规范框架统一

### 3.2 后端通用工程规范（全技术栈适配）

#### 2\.1 通用分层架构（强制统一，所有后端项目适配）

采用经典四层分层架构，适配所有后端语言，分层职责、调用链路全局统一，杜绝架构混乱。

##### 2\.1\.1 标准包结构（通用模板）

```Plain Text
com.xxx.project // 项目根包
├── ProjectApplication        // 唯一服务启动入口
├── config                    // 全局配置类（仅配置、无业务）
├── controller                // 接口控制层
├── service                   // 业务服务层（接口+实现分离）
├── mapper/dao                // 数据访问层
├── entity/model              // 数据库实体模型
├── dto                       // 接口入参数据模型
├── vo                        // 接口出参数据模型
├── common                    // 全局公共能力
│   ├── result                // 统一返回结果封装
│   ├── enums                 // 全局业务枚举
│   ├── exception             // 统一异常体系
│   ├── utils                 // 通用工具类
│   └── constant              // 全局常量
├── security/auth             // 认证授权模块
├── listener/event            // 事件监听、异步处理
├── task/job                  // 定时任务、异步任务
└── util                      // 底层通用工具（无业务依赖）
```

##### 2\.1\.2 分层调用铁律（强制禁止违规）

标准调用链路：Controller → Service\(接口\) → ServiceImpl → Mapper/DAO → 数据库

1. Controller层：仅负责参数接收、参数校验、调用业务服务、封装统一返回结果，禁止编写业务逻辑、直接操作数据库。

2. Service层：承接核心业务逻辑、事务控制、状态流转、跨数据操作，是业务唯一核心层。

3. Mapper/DAO层：仅负责数据库CRUD操作，禁止编写业务判断、事务逻辑。

4. 事务、并发、数据一致性、业务流程流转，全部统一在Service层处理。

5. 禁止跨层调用：Controller禁止直接调用Mapper，Mapper禁止反向调用Service。

#### 2\.2 项目入口规范（通用强制）

1. 每个项目仅保留唯一启动入口类，放置项目根包路径，依靠框架自动包扫描加载组件。

2. 入口类仅保留框架核心启动注解，按需排除冗余自动配置，保持简洁。

3. 启动方法仅执行服务启动逻辑，无自定义初始化业务代码、无硬编码配置。

4. 数据库版本迁移、资源初始化、配置加载，统一交由框架/配置文件管控，不写死在入口。

5. 服务优雅停机、资源释放、连接销毁，通过框架钩子、Bean生命周期自动完成。

#### 2\.3 统一命名规范（全项目通用）

##### 2\.3\.1 类命名规范

- 控制层：XXXController（模块名\+Controller）

- 业务接口：IXXXService（I\+模块名\+Service）

- 业务实现：XXXServiceImpl（模块名\+ServiceImpl）

- 数据层：XXXMapper/XXXDao（模块名\+Mapper/Dao）

- 数据库实体：XXXModel/XXXEntity

- 入参对象：XXXDTO

- 出参对象：XXXVO

- 枚举类：XXXStatusEnum/XXXTypeEnum

- 工具类：XXXUtil

##### 2\.3\.2 方法命名规范（动词\+名词，统一语义）

- 查询类：getById、list、pageList、countTotal

- 新增类：save、submit、create

- 更新类：update、modify、edit

- 删除类：delete、remove（逻辑删除优先）

- 业务操作：auditPass、auditReject、startProcess、cancelTask

##### 2\.3\.3 变量与常量规范

- 布尔变量：isDeleted、isValid、isExpired、hasPermission（语义清晰，见名知意）

- 集合变量：xxxList、xxxMap、xxxSet（统一后缀）

- 常量：全大写下划线命名，统一放置常量类，禁止魔法值

#### 2\.4 通用编码强制约束（全员必守）

1. 禁止魔法数字/魔法字符串：所有状态值、固定参数、配置值统一使用枚举或常量定义。

2. 优先使用卫语句，简化代码分支，嵌套层级禁止超过3层，深层逻辑必须抽取独立方法。

3. 所有接口入参、业务参数必须做合法性校验，空值、长度、格式、范围校验全覆盖。

4. 所有对外接口必须完善接口文档，标注入参、出参、功能说明、异常场景。

5. 敏感数据（手机号、身份证、账号、密钥）日志必须脱敏，禁止明文打印、明文存储。

6. 禁止循环内执行数据库查询、远程调用，批量场景统一批量查询、批量处理。

7. 事务精准控制，拆分大事务、长事务，仅保证核心业务原子性，避免锁表、超时问题。

8. 并发场景必须做防并发处理，通过分布式锁、幂等校验、唯一索引保证数据一致性。

9. 禁止空捕获异常，所有异常必须日志记录、异常兜底，杜绝静默失败。

#### 2\.5 统一接口返回规范（全局通用）

##### 2\.5\.1 固定返回结构（适配所有项目）

所有对外接口统一返回固定格式，包含状态码、提示信息、业务数据，前后端统一对齐。

```Plain Text
{
  "code": 状态码,
  "msg": 提示信息,
  "data": 业务数据/空
}
```

##### 2\.5\.2 通用错误码规范（全局统一）

- 20000：操作成功

- 40001：参数非法、参数校验失败

- 40101：未登录、令牌过期、认证失败

- 40301：权限不足、禁止访问

- 40401：请求资源/数据不存在

- 50001：系统内部异常

- 业务自定义码：6xxxx（专属业务异常，按需扩展）

#### 2\.6 统一异常处理规范

1. 全局统一异常处理器，接管所有接口异常，Controller层禁止手写try\-catch。

2. 自定义业务异常，携带专属错误码与友好提示，区分系统异常与业务异常。

3. 生产环境仅向前端返回友好提示，完整异常堆栈仅留存日志，不对外暴露。

4. 针对数据库异常、锁异常、限流异常、权限异常做单独差异化提示。

5. 所有异常场景必须记录完整错误日志，包含链路信息、操作人、请求参数。

#### 2\.7 通用数据库设计规范

##### 2\.7\.1 数据表通用基础字段（每张表必含）

所有业务数据表统一保留基础审计字段，保证数据可追溯、可恢复。

```Plain Text
id          主键唯一标识
is_deleted  逻辑删除标识（0-未删除，1-已删除）
create_by   创建人ID
create_time 创建时间
update_by   更新人ID
update_time 更新时间
```

##### 2\.7\.2 通用设计约束

1. 表名、字段名统一小写下划线命名，语义清晰、简洁规范。

2. 主键统一使用全局唯一ID，禁止依赖数据库自增（分布式场景适配）。

3. 字段长度合理限制，杜绝无限制超长字符类型，节省存储、提升性能。

4. 时间字段统一使用标准时间类型，规避时区、格式兼容问题。

5. 高频查询字段、状态字段建立普通索引，唯一业务字段建立唯一索引。

6. 禁止数据库外键约束，数据关联完整性统一在代码业务层保障。

7. 大文本、富文本、涉密数据单独存储，与常规业务字段隔离。

8. 敏感业务数据加密存储，杜绝明文留存。

##### 2\.7\.3 数据库版本管控规范

- 所有数据库变更必须编写版本脚本，严格版本递增命名。

- 已上线脚本禁止修改、删除，迭代变更通过新脚本实现，支持版本回溯。

- 数据库初始化、迭代升级、字段变更、索引调整全部纳入版本管控。

#### 2\.8 通用安全编码规范（企业级重点）

1. 防SQL注入：全部使用参数绑定查询，禁止字符串拼接SQL语句。

2. 防XSS攻击：后端富文本内容过滤清洗，前端二次安全校验。

3. 权限安全：接口权限\+数据权限双层校验，杜绝越权查询、越权操作。

4. 密码安全：用户密码加盐哈希不可逆存储，禁止明文、弱加密留存。

5. 令牌安全：认证令牌设置合理有效期，支持主动下线、失效销毁。

6. 接口防护：开启接口限流、防重复提交、防刷机制。

7. 暴力破解防护：登录账号IP锁定、次数限制机制。

8. 配置安全：所有密钥、密码、敏感配置存入环境变量，禁止提交代码仓库。

9. 服务安全：网关/反向代理配置安全响应头，防点击劫持、漏洞遍历。

#### 2\.9 环境与配置通用规范

1. 多环境配置隔离：开发、测试、预发、生产配置文件独立拆分，按需激活。

2. 生产环境关闭所有调试、测试、文档、冗余端点，最小化暴露服务。

3. 中间件开启安全权限、密码认证，禁用危险命令、匿名访问。

4. 数据库、中间件使用最小权限账号，仅分配业务必需权限。

5. 所有配置项禁止硬编码，统一通过环境变量、配置中心读取，适配多环境部署。

#### 2\.10 通用日志规范

1. 日志分级使用：DEBUG（开发调试）、INFO（业务轨迹）、WARN（风险告警）、ERROR（故障异常）。

2. 每条日志必须携带核心追踪信息：链路ID、操作人、请求地址、接口耗时。

3. 敏感数据自动脱敏，杜绝明文日志泄露隐私信息。

4. 日志自动滚动、压缩、清理，避免磁盘占满、日志堆积。

5. 异常日志必须打印完整堆栈信息，保证问题可快速定位。

### 3.3 前端通用工程规范（Vue/React全框架适配）

#### 3\.2 入口文件通用规范

1. 入口文件仅负责框架初始化、插件注册、全局挂载、DOM挂载，不编写业务逻辑。

2. 请求拦截、路由守卫、权限控制、全局异常捕获全部抽离独立文件，入口仅引入初始化。

3. 禁止在入口文件编写接口请求、页面渲染、业务判断逻辑。

4. 区分开发/生产环境配置，生产环境关闭调试工具、开启安全策略。

5. 全局挂载异常捕获机制，防止页面白屏、全局崩溃。

#### 3\.3 前端通用编码规范

1. 统一使用框架最新官方语法规范，遵循组合式、函数式编程思想。

2. 单页面、单组件功能单一，代码精简，超大文件必须拆分重构。

3. 所有接口统一托管至api文件夹，禁止页面内直接编写网络请求。

4. 路由统一懒加载，优化首屏加载速度，减少资源冗余加载。

5. 按钮权限、页面权限统一通过全局指令控制，与后端权限码一一对应。

6. 富文本、用户输入内容统一做安全清洗，杜绝XSS前端漏洞。

7. 全局统一Loading、弹窗提示、错误反馈交互，保证产品体验一致。

8. 通用逻辑、重复代码统一封装hooks/工具类，杜绝代码冗余。

#### 3\.4 接口请求通用规范

1. 统一封装网络请求工具，全局拦截请求、响应、异常。

2. 自动携带认证令牌、请求头参数，统一处理401、403、500等异常状态。

3. 支持重复请求取消、请求防抖、节流，优化网络性能。

4. 统一解析后端通用返回结构，全局统一异常弹窗提示。

5. 分页、排序、筛选参数前后端统一规范，全局对齐。

### 3.4 工程版本与协作通用规范

#### 4\.1 依赖管理规范

1. 项目统一管理依赖版本，集中管控，子模块禁止随意自定义版本号。

2. 生产打包剔除测试依赖、冗余依赖，精简项目体积。

3. 禁止引入快照版、未稳定、废弃依赖，保证项目稳定性。

4. 定期迭代升级安全依赖，修复高危漏洞。

#### 4\.2 Git分支通用规范（标准GitFlow）

- main/master：生产主干分支，永久稳定可部署，禁止直接提交代码。

- dev/develop：开发主干分支，日常功能合并、迭代集成分支。

- feature/xxx：新功能开发分支，从dev分支拉出，开发完成合并回dev。

- hotfix/xxx：线上紧急bug修复分支，从main拉出，修复后合并main\+dev。

- release/vx\.x\.x：版本发布分支，用于版本验收、上线准备。

#### 4\.3 Commit提交注释通用规范

统一语义化提交备注，便于版本追溯、代码评审、迭代复盘：

- feat: 新增xxx功能

- fix: 修复xxx bug

- refactor: 重构xxx代码/逻辑

- perf: 优化xxx性能/体验

- docs: 更新文档、注释

- security: 修复安全漏洞

- style: 调整代码格式、样式

#### 4\.4 通用忽略配置规范

所有项目必须配置忽略文件，禁止提交冗余、敏感、本地配置文件：IDE配置、依赖缓存、日志文件、环境配置、密钥文件、临时文件、编译产物。

#### 4\.5 代码评审（Code Review）强制检查清单（新增）

所有代码合并前必须完成CR评审，严格执行5项必查清单，任意一项不达标禁止合并代码：

1. 是否存在魔法值、魔法字符串未替换为常量或枚举，是否存在硬编码业务参数。

2. 是否存在循环内数据库查询、循环内远程调用、循环内事务开启等低效代码。

3. 是否存在手机号、身份证、密钥、用户隐私等敏感数据明文打印、明文存储、明文传输问题。

4. 所有对外接口、业务入口是否完成完整参数校验，包含非空、长度、格式、范围、业务合法性校验。

5. 所有异常场景是否被妥善捕获，是否打印完整日志，是否存在空catch吞异常、静默失败问题。

拓展抽检项：分层调用是否合规、事务范围是否合理、是否存在接口越权风险、代码是否可复用、是否存在冗余逻辑。

#### 4\.6 代码重构阈值与代码坏味道识别标准（新增）

为避免代码腐化、技术债务堆积，定义统一重构触发阈值，达到任意条件必须进行代码重构优化，禁止带病迭代。

##### 4\.6\.1 强制重构阈值（满足即重构）

1. 单个方法代码行数超过80行，存在大量冗余逻辑、分支嵌套。

2. 代码分支嵌套层级超过3层，阅读性、维护性极差。

3. 同一业务逻辑重复出现3次及以上，未做统一封装抽取。

4. 接口响应缓慢、数据库查询存在全表扫描、未建索引，连续迭代无法修复性能问题。

5. 原有代码频繁出现bug，迭代修改频次高、改动范围大。

6. 业务场景持续扩展，原有if\-else分支无限膨胀，无法维护。

7. 核心业务代码无注释、无说明，团队多人无法理解逻辑。

##### 4\.6\.2 核心代码坏味道识别标准

1. 魔法值泛滥：大量硬编码数字、字符串，无枚举、无常量统一管理。

2. 臃肿方法：单一方法承担多类业务职责，违背单一职责原则。

3. 冗余嵌套：大量if\-else、for嵌套，代码可读性差。

4. 重复代码：相同逻辑分散在多个方法、多个模块，未统一封装。

5. 空异常捕获：catch空实现、无日志、无兜底，问题无法排查。

6. 跨层乱调用：分层架构混乱，直接跨层调用数据、业务逻辑。

7. 大事务滥用：事务范围过大，包含无关查询、日志、远程调用，引发锁超时。

8. 资源不释放：连接、流、线程资源未手动关闭，存在内存泄漏风险。

## 4. 入口文件标准化规范

### 4.1 全语言通用顶层强制纲领（所有框架/前后端统一遵守）

#### （一）入口文件核心定位（唯一不变定义）

1. 身份定性：仅作为**应用容器装配器、依赖加载调度器、生命周期总管家、安全前置校验闸门**，不承载任何业务功能。
2. 不可突破红线：所有业务逻辑、数据处理、接口实现、页面交互必须全部下沉至分层目录，入口零业务侵入。

#### （二）全栈统一通用约束规则

1. **加载顺序强制范式（固定流水线）**
基础环境与配置加载 → 安全能力全局注册 → 第三方中间件/存储连接初始化 → 框架核心实例创建 → 路由/权限体系挂载 → 公共工具与通用组件注入 → 应用启动/页面挂载 → 注册退出销毁钩子。

2. **启动快速失败机制（全语言标配）**
启动阶段校验数据库、缓存、加密密钥、签名密钥等核心必填配置；参数缺失、连接不可用时直接终止程序，拒绝带病运行；日志输出敏感信息必须脱敏掩码，禁止明文打印账号、密钥、密码。

3. **优雅停机闭环要求**
全部入口必须绑定系统信号/进程销毁事件，执行统一资源回收：关闭数据库连接池、缓存连接、异步线程池、定时任务、工作流引擎后台执行器、消息消费客户端，设置固定超时等待时长，避免任务悬空、数据不一致、锁未释放问题。

4. **环境隔离硬性规则**
入口不硬编码地址、端口、开关、密钥；全部通过环境变量、外部配置文件读取；仅读取激活环境用于日志打印，不编写复杂环境判断分支逻辑。

5. **可观测性统一要求**
内置启动耗时统计、运行环境标记；生产环境关闭调试模式、精简日志；预留监控指标埋点入口，便于对接监控告警体系。

6. **体积与轻量化约束**
入口仅引入框架核心依赖与安全类基础包，大型重型组件、业务组件禁止在入口直接引入，采用异步懒加载、按需引入方案，控制入口文件整体大小。

#### （三）命名与存放路径通用标准

##### 1）后端服务类入口

- Java/SpringBoot：顶层根包下，命名为`项目名Application`
- Go：项目根目录`main.go`
- Python：项目根目录`main.py`/`app.py`
- Node.js/TypeScript后端：根目录`index.ts`/`main.ts`
- PHP：项目入口`index.php`

统一存放规则：放置在源码最外层一级目录，不嵌套业务模块包内。

##### 2）前端SPA应用入口

- Vue3：src根目录`main.js/main.ts`
- React：src根目录`main.tsx/index.tsx`
- UniApp/小程序：项目根目录`main.js`

统一存放规则：固定在src源码根路径，不放入views、pages等业务文件夹。

#### （四）全语言禁止黑名单（Code Review直接驳回）

1. 禁止硬编码任何IP、端口、域名、密钥、账号密码；
2. 禁止在入口编写判断分支、循环计算、数据增删改查逻辑；
3. 禁止使用原生控制台无规范打印，统一使用项目封装日志组件；
4. 禁止大量重量级依赖直接导入入口，造成启动臃肿；
5. 禁止直接实例化业务层对象、调用业务方法。

### 4.2 后端不同技术栈入口标准化规范（纯规则）

#### 1. Java SpringBoot 体系

1. 包扫描：显式指定扫描包路径，禁用模糊通配符扫描，避免Flowable引擎Bean冲突覆盖；
2. 注解约束：必须开启Mapper扫描、异步支持，显式排除热部署工具类防止生产内存泄漏；
3. 内部结构：仅保留启动主方法、配置校验后置执行器、销毁生命周期钩子；
4. 校验能力：启动校验核心配置完整性，BPMN流程文件可用性仅告警不阻断服务；
5. 销毁动作：钩子中联动配置类关闭Flowable异步执行线程池，设置30秒等待周期收尾运行中审批任务。

#### 2. Go Gin/Echo 体系

1. 分层解耦：配置加载、容器初始化、路由注册全部抽离独立包，入口仅做顺序调用；
2. 信号监听：监听操作系统退出信号，触发延迟关闭，等待请求处理完毕再释放连接；
3. 中间件顺序：安全校验、签名验签、限流中间件最先注册，路由最后挂载。

#### 3. Python Flask/FastAPI 体系

1. 延迟创建：应用实例、数据库连接采用工厂模式外部封装，入口仅调用工厂方法；
2. 事件绑定：通过生命周期事件绑定启动校验与关闭回收逻辑；
3. 生产模式：入口区分uvicorn/gunicorn部署启动参数，不内嵌服务启动参数。

#### 4. Node.js Express/NestJS 体系

1. Nest框架：入口仅引导Nest容器创建，模块、拦截器、过滤器全部在Module层定义；
2. 进程守护：捕获未捕获异常、未拒绝Promise，绑定SIGINT/SIGTERM信号优雅关停；
3. 安全前置：全局拦截器、跨域、请求验签在实例挂载最早期注册。

### 4.3 前端不同技术栈入口标准化规范（纯规则）

#### 1. Vue3 Vite 体系

1. 加载顺序固定：XSS净化指令 → 请求拦截器（Token+签名）→ 状态管理 → 路由权限守卫 → UI组件 → 全局组件 → 挂载；
2. 白屏治理：路由就绪前开启全局加载遮罩，权限拉取设置超时兜底路由，避免无限加载卡死；
3. 环境管控：生产环境关闭调试工具、性能检测，全局统一异常捕获防止页面崩溃；
4. 体积管控：ECharts、表格导出、富文本等大型库全部页面内按需引入，入口文件体积严格管控。

#### 2. React Vite/Webpack 体系

1. 入口职责：仅渲染根路由组件，路由守卫、请求封装、全局状态全部抽离独立文件；
2. 异常兜底：全局ErrorBoundary在最外层挂载，捕获组件渲染异常；
3. 安全统一：Axios请求拦截、XSS过滤、敏感内容转义在入口全局注入。

#### 3. 小程序/跨端项目

1. App.onLaunch仅做初始化配置、登录态预校验；
2. 请求拦截、权限校验、全局错误监听统一在入口生命周期内注册；
3. 不编写页面跳转、业务数据请求逻辑。

### 4.4 长期落地治理保障方案

1. **脚手架模板固化**
将各语言入口规范骨架内置到项目脚手架、Archetype、Vite预设模板，新项目自动生成合规入口，杜绝人工手写偏差。

2. **静态代码扫描卡点**
通过Sonar、ESLint、Pylint、golint配置自定义规则：
- 检测入口文件行数超标、违规导入重量级依赖；
- 检测硬编码IP/密钥、违规业务代码写入入口；
- 检测缺少关闭钩子、缺少启动配置校验等缺失项。

3. **CR评审固定检查项**
将「入口文件是否符合通用规范」设置为MR/PR必过卡点，不合规直接打回重构。
