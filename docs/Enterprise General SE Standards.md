# 企业级通用软件工程规范体系

适用范围：全行业企业级软件项目，适配Java/Go/Python后端、Vue/React前端、各类数据库、中间件及容器化部署架构，无技术栈绑定，可直接落地各类业务系统（OA、工单、审批、电商、管理平台等）

落地方式：直接放入项目 docs/DEVELOPMENT\_SPEC\.md，作为团队统一研发标准、新人入职规范、项目交付验收依据

# 一、总则

## 1\.1 核心设计原则（全局强制约束）

所有研发工作、代码编写、架构设计、流程搭建必须遵循以下顶层原则，作为项目唯一评判标准：

1. 单一职责原则：类、方法、接口、组件仅负责单一功能，入口类仅启动服务，不承载任何业务逻辑。

2. 高内聚低耦合原则：模块内部功能高度聚合，模块间通过标准化接口通信，禁止硬编码耦合、跨模块直接调用内部逻辑。

3. 开闭原则：对功能扩展开放，对原有代码修改关闭，复杂分支、多场景逻辑通过设计模式优化，杜绝多层冗余if\-else。

4. 依赖倒置原则：高层业务逻辑依赖抽象接口，不依赖具体实现类，便于迭代扩展、替换实现方案。

5. 最小权限原则：系统账号、文件权限、接口访问、数据操作、服务调用均遵循最小可用权限，杜绝超权限配置。

6. 可观测性原则：日志、异常捕获、业务埋点、服务监控、链路追踪全覆盖，所有故障、问题可追溯、可定位、可复盘。

7. 环境隔离原则：开发、测试、预发、生产环境严格隔离配置、数据、资源，禁止生产环境开启调试、测试、冗余功能开关。

8. 可复用可维护原则：通用逻辑、工具方法、业务组件统一封装，代码简洁规范，便于迭代维护、多人协作。

## 1\.2 通用技术栈标准化准则与技术选型准入标准

本规范不强制固定技术栈，仅定义企业级通用技术选型标准，各项目可根据业务场景适配，统一团队技术范式。所有新增技术、开源组件、框架、中间件必须遵循统一准入评审流程。

### 1\.2\.1 基础技术选型方向

- 核心框架：采用主流稳定开源框架，优先官方长期维护版本，杜绝小众、废弃框架

- 权限体系：统一基于RBAC角色权限模型，支持接口级、数据级双层权限控制

- 数据层：使用标准化ORM框架，杜绝原生硬编码SQL，保证数据操作统一规范

- 数据存储：关系型数据库为主、缓存中间件为辅，复杂场景适配时序、文档数据库

- 版本管理：数据库脚本版本化管控，支持自动迁移、版本回溯

- 服务监控：接入通用监控、链路追踪组件，实现服务状态、接口性能、异常全监控

- 工具依赖：选用社区活跃、安全稳定的通用工具类，禁止自定义冗余底层工具

### 1\.2\.2 技术选型准入评审强制规范（新增）

项目所有新增技术框架、开源组件、中间件、工具依赖，必须经过架构组评审通过后方可引入，禁止研发人员私自新增、替换技术依赖。评审核心维度如下：

1. 社区活跃度：核查项目Star数量、近期Commit频率、版本迭代节奏，杜绝长期停滞、无人维护的组件。

2. 安全风险：查询公开漏洞库，确认无高危、未修复漏洞，无历史重大安全事故。

3. 团队技术储备：匹配现有团队技术能力，避免引入学习成本过高、无人维护的技术体系。

4. 长期维护成本：评估版本迭代稳定性、文档完善度、问题排查成本，适配企业长期迭代需求。

5. 技术兼容性：与项目现有技术栈、工程架构、部署体系兼容，无版本冲突、架构冲突。

强制红线：禁止引入无官方LTS长期支持版本、已停止迭代、社区废弃的开源组件及框架。

## 1\.3 通用术语与约束

- 强制规范：所有项目必须严格遵守，违规视为代码不合格，禁止合并上线

- 推荐规范：最优实践方案，新项目严格执行，存量迭代逐步优化

- 业务适配项：根据项目业务场景灵活调整，保持整体规范框架统一

# 二、后端通用工程规范（全技术栈适配）

## 2\.1 通用分层架构（强制统一，所有后端项目适配）

采用经典四层分层架构，适配所有后端语言，分层职责、调用链路全局统一，杜绝架构混乱。

### 2\.1\.1 标准包结构（通用模板）

```Plain Text
com.xxx.project // 项目根包
├── ProjectApplication        // 唯一服务启动入口
├── config                    // 全局配置类（仅配置、无业务）
├── controller                // 接口控制层
├── service                   // 业务服务层（接口+实现分离）
├── mapper/dao                // 数据访问层
├── entity/model              // 数据库实体模型
├── dto                       // 接口入参数据模型
├── vo                        // 接口出参数据模型
├── common                    // 全局公共能力
│   ├── result                // 统一返回结果封装
│   ├── enums                 // 全局业务枚举
│   ├── exception             // 统一异常体系
│   ├── utils                 // 通用工具类
│   └── constant              // 全局常量
├── security/auth             // 认证授权模块
├── listener/event            // 事件监听、异步处理
├── task/job                  // 定时任务、异步任务
└── util                      // 底层通用工具（无业务依赖）
```

### 2\.1\.2 分层调用铁律（强制禁止违规）

标准调用链路：Controller → Service\(接口\) → ServiceImpl → Mapper/DAO → 数据库

1. Controller层：仅负责参数接收、参数校验、调用业务服务、封装统一返回结果，禁止编写业务逻辑、直接操作数据库。

2. Service层：承接核心业务逻辑、事务控制、状态流转、跨数据操作，是业务唯一核心层。

3. Mapper/DAO层：仅负责数据库CRUD操作，禁止编写业务判断、事务逻辑。

4. 事务、并发、数据一致性、业务流程流转，全部统一在Service层处理。

5. 禁止跨层调用：Controller禁止直接调用Mapper，Mapper禁止反向调用Service。

## 2\.2 项目入口规范（通用强制）

1. 每个项目仅保留唯一启动入口类，放置项目根包路径，依靠框架自动包扫描加载组件。

2. 入口类仅保留框架核心启动注解，按需排除冗余自动配置，保持简洁。

3. 启动方法仅执行服务启动逻辑，无自定义初始化业务代码、无硬编码配置。

4. 数据库版本迁移、资源初始化、配置加载，统一交由框架/配置文件管控，不写死在入口。

5. 服务优雅停机、资源释放、连接销毁，通过框架钩子、Bean生命周期自动完成。

## 2\.3 统一命名规范（全项目通用）

### 2\.3\.1 类命名规范

- 控制层：XXXController（模块名\+Controller）

- 业务接口：IXXXService（I\+模块名\+Service）

- 业务实现：XXXServiceImpl（模块名\+ServiceImpl）

- 数据层：XXXMapper/XXXDao（模块名\+Mapper/Dao）

- 数据库实体：XXXModel/XXXEntity

- 入参对象：XXXDTO

- 出参对象：XXXVO

- 枚举类：XXXStatusEnum/XXXTypeEnum

- 工具类：XXXUtil

### 2\.3\.2 方法命名规范（动词\+名词，统一语义）

- 查询类：getById、list、pageList、countTotal

- 新增类：save、submit、create

- 更新类：update、modify、edit

- 删除类：delete、remove（逻辑删除优先）

- 业务操作：auditPass、auditReject、startProcess、cancelTask

### 2\.3\.3 变量与常量规范

- 布尔变量：isDeleted、isValid、isExpired、hasPermission（语义清晰，见名知意）

- 集合变量：xxxList、xxxMap、xxxSet（统一后缀）

- 常量：全大写下划线命名，统一放置常量类，禁止魔法值

## 2\.4 通用编码强制约束（全员必守）

1. 禁止魔法数字/魔法字符串：所有状态值、固定参数、配置值统一使用枚举或常量定义。

2. 优先使用卫语句，简化代码分支，嵌套层级禁止超过3层，深层逻辑必须抽取独立方法。

3. 所有接口入参、业务参数必须做合法性校验，空值、长度、格式、范围校验全覆盖。

4. 所有对外接口必须完善接口文档，标注入参、出参、功能说明、异常场景。

5. 敏感数据（手机号、身份证、账号、密钥）日志必须脱敏，禁止明文打印、明文存储。

6. 禁止循环内执行数据库查询、远程调用，批量场景统一批量查询、批量处理。

7. 事务精准控制，拆分大事务、长事务，仅保证核心业务原子性，避免锁表、超时问题。

8. 并发场景必须做防并发处理，通过分布式锁、幂等校验、唯一索引保证数据一致性。

9. 禁止空捕获异常，所有异常必须日志记录、异常兜底，杜绝静默失败。

## 2\.5 统一接口返回规范（全局通用）

### 2\.5\.1 固定返回结构（适配所有项目）

所有对外接口统一返回固定格式，包含状态码、提示信息、业务数据，前后端统一对齐。

```Plain Text
{
  "code": 状态码,
  "msg": 提示信息,
  "data": 业务数据/空
}
```

### 2\.5\.2 通用错误码规范（全局统一）

- 20000：操作成功

- 40001：参数非法、参数校验失败

- 40101：未登录、令牌过期、认证失败

- 40301：权限不足、禁止访问

- 40401：请求资源/数据不存在

- 50001：系统内部异常

- 业务自定义码：6xxxx（专属业务异常，按需扩展）

## 2\.6 统一异常处理规范

1. 全局统一异常处理器，接管所有接口异常，Controller层禁止手写try\-catch。

2. 自定义业务异常，携带专属错误码与友好提示，区分系统异常与业务异常。

3. 生产环境仅向前端返回友好提示，完整异常堆栈仅留存日志，不对外暴露。

4. 针对数据库异常、锁异常、限流异常、权限异常做单独差异化提示。

5. 所有异常场景必须记录完整错误日志，包含链路信息、操作人、请求参数。

## 2\.7 通用数据库设计规范

### 2\.7\.1 数据表通用基础字段（每张表必含）

所有业务数据表统一保留基础审计字段，保证数据可追溯、可恢复。

```Plain Text
id          主键唯一标识
is_deleted  逻辑删除标识（0-未删除，1-已删除）
create_by   创建人ID
create_time 创建时间
update_by   更新人ID
update_time 更新时间
```

### 2\.7\.2 通用设计约束

1. 表名、字段名统一小写下划线命名，语义清晰、简洁规范。

2. 主键统一使用全局唯一ID，禁止依赖数据库自增（分布式场景适配）。

3. 字段长度合理限制，杜绝无限制超长字符类型，节省存储、提升性能。

4. 时间字段统一使用标准时间类型，规避时区、格式兼容问题。

5. 高频查询字段、状态字段建立普通索引，唯一业务字段建立唯一索引。

6. 禁止数据库外键约束，数据关联完整性统一在代码业务层保障。

7. 大文本、富文本、涉密数据单独存储，与常规业务字段隔离。

8. 敏感业务数据加密存储，杜绝明文留存。

### 2\.7\.3 数据库版本管控规范

- 所有数据库变更必须编写版本脚本，严格版本递增命名。

- 已上线脚本禁止修改、删除，迭代变更通过新脚本实现，支持版本回溯。

- 数据库初始化、迭代升级、字段变更、索引调整全部纳入版本管控。

## 2\.8 通用安全编码规范（企业级重点）

1. 防SQL注入：全部使用参数绑定查询，禁止字符串拼接SQL语句。

2. 防XSS攻击：后端富文本内容过滤清洗，前端二次安全校验。

3. 权限安全：接口权限\+数据权限双层校验，杜绝越权查询、越权操作。

4. 密码安全：用户密码加盐哈希不可逆存储，禁止明文、弱加密留存。

5. 令牌安全：认证令牌设置合理有效期，支持主动下线、失效销毁。

6. 接口防护：开启接口限流、防重复提交、防刷机制。

7. 暴力破解防护：登录账号IP锁定、次数限制机制。

8. 配置安全：所有密钥、密码、敏感配置存入环境变量，禁止提交代码仓库。

9. 服务安全：网关/反向代理配置安全响应头，防点击劫持、漏洞遍历。

## 2\.9 环境与配置通用规范

1. 多环境配置隔离：开发、测试、预发、生产配置文件独立拆分，按需激活。

2. 生产环境关闭所有调试、测试、文档、冗余端点，最小化暴露服务。

3. 中间件开启安全权限、密码认证，禁用危险命令、匿名访问。

4. 数据库、中间件使用最小权限账号，仅分配业务必需权限。

5. 所有配置项禁止硬编码，统一通过环境变量、配置中心读取，适配多环境部署。

## 2\.10 通用日志规范

1. 日志分级使用：DEBUG（开发调试）、INFO（业务轨迹）、WARN（风险告警）、ERROR（故障异常）。

2. 每条日志必须携带核心追踪信息：链路ID、操作人、请求地址、接口耗时。

3. 敏感数据自动脱敏，杜绝明文日志泄露隐私信息。

4. 日志自动滚动、压缩、清理，避免磁盘占满、日志堆积。

5. 异常日志必须打印完整堆栈信息，保证问题可快速定位。

# 三、前端通用工程规范（Vue/React全框架适配）

## 3\.1 通用目录结构（强制统一）

```Plain Text
src
├── main.ts/main.js        // 唯一入口文件
├── App.vue/App.jsx        // 根组件
├── api                    // 统一接口请求管理
├── router                 // 路由配置+路由守卫
├── store                  // 全局状态管理
├── views                  // 页面视图（按业务模块分包）
├── components             // 组件库
│   ├── common             // 全局公共通用组件
│   └── business           // 业务专属组件
├── directives             // 自定义全局指令
├── hooks/composables      // 通用组合式工具方法
├── utils                  // 前端通用工具函数
├── styles                 // 全局样式、重置样式、主题样式
├── constants              // 全局常量、枚举、状态映射
└── types                  // 全局TS类型定义（TS项目强制）
```

## 3\.2 入口文件通用规范

1. 入口文件仅负责框架初始化、插件注册、全局挂载、DOM挂载，不编写业务逻辑。

2. 请求拦截、路由守卫、权限控制、全局异常捕获全部抽离独立文件，入口仅引入初始化。

3. 禁止在入口文件编写接口请求、页面渲染、业务判断逻辑。

4. 区分开发/生产环境配置，生产环境关闭调试工具、开启安全策略。

5. 全局挂载异常捕获机制，防止页面白屏、全局崩溃。

## 3\.3 前端通用编码规范

1. 统一使用框架最新官方语法规范，遵循组合式、函数式编程思想。

2. 单页面、单组件功能单一，代码精简，超大文件必须拆分重构。

3. 所有接口统一托管至api文件夹，禁止页面内直接编写网络请求。

4. 路由统一懒加载，优化首屏加载速度，减少资源冗余加载。

5. 按钮权限、页面权限统一通过全局指令控制，与后端权限码一一对应。

6. 富文本、用户输入内容统一做安全清洗，杜绝XSS前端漏洞。

7. 全局统一Loading、弹窗提示、错误反馈交互，保证产品体验一致。

8. 通用逻辑、重复代码统一封装hooks/工具类，杜绝代码冗余。

## 3\.4 接口请求通用规范

1. 统一封装网络请求工具，全局拦截请求、响应、异常。

2. 自动携带认证令牌、请求头参数，统一处理401、403、500等异常状态。

3. 支持重复请求取消、请求防抖、节流，优化网络性能。

4. 统一解析后端通用返回结构，全局统一异常弹窗提示。

5. 分页、排序、筛选参数前后端统一规范，全局对齐。

# 四、工程版本与协作通用规范

## 4\.1 依赖管理规范

1. 项目统一管理依赖版本，集中管控，子模块禁止随意自定义版本号。

2. 生产打包剔除测试依赖、冗余依赖，精简项目体积。

3. 禁止引入快照版、未稳定、废弃依赖，保证项目稳定性。

4. 定期迭代升级安全依赖，修复高危漏洞。

## 4\.2 Git分支通用规范（标准GitFlow）

- main/master：生产主干分支，永久稳定可部署，禁止直接提交代码。

- dev/develop：开发主干分支，日常功能合并、迭代集成分支。

- feature/xxx：新功能开发分支，从dev分支拉出，开发完成合并回dev。

- hotfix/xxx：线上紧急bug修复分支，从main拉出，修复后合并main\+dev。

- release/vx\.x\.x：版本发布分支，用于版本验收、上线准备。

## 4\.3 Commit提交注释通用规范

统一语义化提交备注，便于版本追溯、代码评审、迭代复盘：

- feat: 新增xxx功能

- fix: 修复xxx bug

- refactor: 重构xxx代码/逻辑

- perf: 优化xxx性能/体验

- docs: 更新文档、注释

- security: 修复安全漏洞

- style: 调整代码格式、样式

## 4\.4 通用忽略配置规范

所有项目必须配置忽略文件，禁止提交冗余、敏感、本地配置文件：IDE配置、依赖缓存、日志文件、环境配置、密钥文件、临时文件、编译产物。

## 4\.5 代码评审（Code Review）强制检查清单（新增）

所有代码合并前必须完成CR评审，严格执行5项必查清单，任意一项不达标禁止合并代码：

1. 是否存在魔法值、魔法字符串未替换为常量或枚举，是否存在硬编码业务参数。

2. 是否存在循环内数据库查询、循环内远程调用、循环内事务开启等低效代码。

3. 是否存在手机号、身份证、密钥、用户隐私等敏感数据明文打印、明文存储、明文传输问题。

4. 所有对外接口、业务入口是否完成完整参数校验，包含非空、长度、格式、范围、业务合法性校验。

5. 所有异常场景是否被妥善捕获，是否打印完整日志，是否存在空catch吞异常、静默失败问题。

拓展抽检项：分层调用是否合规、事务范围是否合理、是否存在接口越权风险、代码是否可复用、是否存在冗余逻辑。

## 4\.6 代码重构阈值与代码坏味道识别标准（新增）

为避免代码腐化、技术债务堆积，定义统一重构触发阈值，达到任意条件必须进行代码重构优化，禁止带病迭代。

### 4\.6\.1 强制重构阈值（满足即重构）

1. 单个方法代码行数超过80行，存在大量冗余逻辑、分支嵌套。

2. 代码分支嵌套层级超过3层，阅读性、维护性极差。

3. 同一业务逻辑重复出现3次及以上，未做统一封装抽取。

4. 接口响应缓慢、数据库查询存在全表扫描、未建索引，连续迭代无法修复性能问题。

5. 原有代码频繁出现bug，迭代修改频次高、改动范围大。

6. 业务场景持续扩展，原有if\-else分支无限膨胀，无法维护。

7. 核心业务代码无注释、无说明，团队多人无法理解逻辑。

### 4\.6\.2 核心代码坏味道识别标准

1. 魔法值泛滥：大量硬编码数字、字符串，无枚举、无常量统一管理。

2. 臃肿方法：单一方法承担多类业务职责，违背单一职责原则。

3. 冗余嵌套：大量if\-else、for嵌套，代码可读性差。

4. 重复代码：相同逻辑分散在多个方法、多个模块，未统一封装。

5. 空异常捕获：catch空实现、无日志、无兜底，问题无法排查。

6. 跨层乱调用：分层架构混乱，直接跨层调用数据、业务逻辑。

7. 大事务滥用：事务范围过大，包含无关查询、日志、远程调用，引发锁超时。

8. 资源不释放：连接、流、线程资源未手动关闭，存在内存泄漏风险。

# 五、全流程测试通用规范

## 5\.1 测试分层规范

1. 单元测试：核心业务逻辑、工具方法、通用算法必须编写单元测试，保证基础功能可靠。

2. 接口测试：所有对外接口覆盖正向、反向场景，留存完整测试用例。

3. 功能测试：全覆盖业务流程、正常场景、异常场景、边界场景。

4. 兼容性测试：适配浏览器、终端、系统版本、环境差异。

5. 性能测试：核心接口、高频功能做并发、压测、耗时优化测试。

6. 安全测试：覆盖越权访问、注入攻击、XSS、重复提交、令牌劫持等场景。

## 5\.2 上线测试门禁（强制）

所有功能上线前必须完成：边界测试、异常测试、并发测试、安全测试，无致命bug、无高危漏洞、无性能瓶颈方可上线。

# 六、部署运维通用规范

## 6\.1 打包构建规范

1. 项目分层打包，剔除冗余资源，精简部署包体积。

2. 区分环境打包，生产包关闭调试功能、开启安全配置。

3. 禁止测试包、开发包直接上线，严格区分部署包版本。

## 6\.2 容器化部署通用规范

1. 统一容器化打包，标准化镜像构建流程，保证环境一致性。

2. 通过编排工具统一管理服务、中间件依赖，一键部署、启停。

3. 生产环境实现服务高可用、负载均衡，避免单点故障。

## 6\.3 运维监控与安全规范

1. 统一配置HTTPS、请求限流、资源缓存、安全防护策略。

2. 数据库开启定时备份、故障恢复机制，保障数据安全。

3. 接入服务监控、性能监控、异常告警，故障实时感知。

4. 配置告警规则：服务宕机、接口异常、性能骤降、资源耗尽。

# 七、项目文档通用交付规范

所有企业级项目必须配齐标准化文档，实现可交付、可维护、可交接：

1. README\.md：项目简介、技术栈、启动方式、环境依赖、快速上手教程。

2. DEVELOPMENT\_SPEC\.md：本通用研发规范，团队统一执行标准。

3. API\_DOC\.md：全量接口文档、入参出参、错误码、调用示例。

4. DB\_DESIGN\.md：数据库设计文档、表结构、字段说明、索引设计、ER图。

5. DEPLOY\_GUIDE\.md：部署手册、环境配置、启动命令、版本升级、回滚方案。

6. SECURITY\_CHECKLIST\.md：上线安全自查清单、漏洞修复、合规校验。

7. ARCHITECTURE\.md：系统架构设计、模块拆分、核心流程、技术方案说明。
